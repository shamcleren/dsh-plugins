# Unified repository and first installation

This repository owns plugin sources, release artifacts, the official runtime lock, and the macOS shell. Separate npm packages preserve independent configuration and removal; separate Git repositories are not required. Source imports preserve the Marketplace `3328d1e`, Codex Controller `4219d7f`, and macOS shell `eeab3ea` revisions and their licenses. Their GitHub repositories are not deleted or archived by this change.

`make init` invokes a POSIX shell preflight so Node.js and npm are not prerequisites. It reuses a compatible installed pair, or downloads a pinned official Node.js archive into a private temporary directory and verifies SHA-256 before extraction/execution. The shell and macOS app builder share `runtime/node-release.sha256`. The locked runtime installer copies the verified distribution into its own `node/` directory and emits an executable `bin/dsh` bound to that installation’s Node.js. It also writes `bin/dhp` and a user-local symlink at `~/.local/bin/dhp`. If that directory is not already on PATH, a marked `export PATH` line is appended to the user shell profile. Temporary downloads are removed after completion or failure; no global npm package or unrelated installation is changed. Git/make (or the shell fallback), download/checksum tools, and macOS developer tools remain explicit prerequisites.

The installer defaults to official DSH with its native plugin UI and no additional repository plugins. Configuration, credentials, sessions and profiles use the shared `~/.dsh` root. Existing settings and profile plugins are reused; a fresh installation directory does not imply an empty profile. It installs the frozen official npm runtime with lifecycle scripts disabled; this path does not read the repository catalog or plugin artifacts. With explicit `--with-marketplace`, it uses the repository catalog to identify one trusted Marketplace tarball, validates byte size, SHA-256, package identity, artifact path, and the exact compatible DSH version before creating installation state, then invokes the official `dsh plugin --profile web add` flow. The remote bundle uses its own `trusted-marketplace` tab without claiming the `marketplace` ID or replacing native plugin tabs. Source configuration and authorization remain optional. No source checkout, global npm install, or existing profile is needed.

An exclusively created installation directory and marker distinguish installer-owned data from user directories. A filesystem lock excludes concurrent writers. Repeating a completed installation updates the repository-pinned runtime when its lock changes and rebuilds the App when its sources, runtime, signing identity or port change; unchanged inputs are reused. `REBUILD=1` forces an App rebuild. It never follows upstream `latest`. Installed profile packages must accept the staged runtime's DSH peer versions before publication; functional compatibility remains a release verification responsibility.

Updates stage runtime, launchers and App beneath the installation root, verify builds before publication, then record a journal and retain old files until final verification succeeds. Failures roll back; an interrupted transaction is recovered on the next run after the lock has been safely cleared. App/Web processes belonging to the installation must be closed; new launchers refuse to start during installation or pending recovery. The installer never kills processes or removes stale locks automatically. Existing custom desktop ports are read from the App record or legacy Info.plist unless explicitly overridden.

The schema-v2 marker records the selected absolute `dshHome`, a null Marketplace digest for basic installations and the verified digest for opted-in installations. Failed first installation requires explicit resume with the original options. Completed schema-v1 installations can update while retaining `<installation>/home`; there is no implicit data migration. Repeating init preserves settings, credentials, sessions and profile plugins. An installation originally created with Marketplace can later use `dhp update`; adding or updating plugins uses the official CLI through `dhp plugin install` or the remote UI rather than changing bootstrap mode. Make remains only the no-Node first-install entry point. After initialization, `dhp` is a user command bound to that installation; optional plugin commands stay behind the generic `dhp plugin exec` boundary.

On macOS, Xcode Command Line Tools are checked before package installation. The native shell copies the installed official runtime and a SHA-256-pinned Node distribution into its app bundle. Its `DSHInstallationRoot` Info.plist value selects installation-owned auxiliary paths. The `DSHHome` value and bootstrap marker pin the same configuration root for the native and Web launchers, defaulting to `~/.dsh`. New standalone shell builds use this default too. Existing settings are not migrated or reset. Separately installed DSH instances with the same home share their configuration and must not run concurrently against that profile. The application is locally signed and does not replace or terminate a pre-existing installation.

Unit tests cover rejected inputs, concurrent ownership, failure/resume, and idempotence without network services. Native tests compile the shell and execute its path selection. Release verification must run the real bootstrap into a new private directory, inspect the installed profile and app plist, start the official Web profile on an OS-assigned port, and confirm the native plugin configuration and inventory remain available alongside the optional remote tab after adding its release bundle, without configuring remote credentials. The pinned official rc.8 distribution does not include a marketplace tab by default. Coexistence with a separately installed marketplace requires testing that provider as well. Live credentials, bot activation, and user-data migration remain explicit user operations.

New installations default to the repository `dist/` directory, with `DeepSeek Harness.app` directly inside it and runtime files in sibling subdirectories. `DIR` still overrides this root, and `~/.dsh` remains the default data root. Existing user-directory installations are not moved or adopted. Plugin commands use the same repository-local default; selecting an old installation requires its explicit `DIR`. Existing `apps/*.app` metadata remains readable.
