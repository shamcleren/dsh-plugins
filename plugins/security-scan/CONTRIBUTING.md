# Contributing

Issues and pull requests are welcome in [shamcleren/dsh-security-scan](https://github.com/shamcleren/dsh-security-scan). The maintainer develops the plugin in a private source repository and publishes this repository as a sanitized export, so an accepted pull request is ported into that source and arrives here with the next export instead of being merged directly. Do not edit generated release archives or installed profile copies.

Use the committed `pnpm-lock.yaml` and the pnpm version in `packageManager`: `pnpm install --frozen-lockfile --ignore-scripts`, then `pnpm typecheck`, `pnpm test` and `pnpm build`. `lib/` is the build of the current release; pull requests do not need to update it. Behavioral changes need regression coverage. Edit rules in `scripts/build-rules.mjs` and regenerate `rules/baseline.yml` with `node scripts/build-rules.mjs`; never edit the generated file by hand. For scanner/rule changes, add focused regression coverage and opt in to real scanner tests with `SECURITY_TEST_SEMGREP=/absolute/path/semgrep`. Review every changed outcome; never lower a gate to hide regressions. Tests use temporary directories, fake account data and no model credentials. Do not run fixtures or target project code.

Keep user text localized and tools under `dsh_security_scan_`; keep the Skill `dsh-security-review`. Use only public DSH extension points and declare actual dependencies. Do not widen runtime compatibility based only on typechecks. New listeners, processes and queued work need an owner and cleanup. Inputs, paths, external responses and persisted data need bounded validation; failure or partial coverage must not appear as a clean scan.

Update the authoritative docs and migration notes with behavior changes. Keep reports free of credential values and raw scanner stderr. Add original/licensed, independently labelled benchmark cases with explicit assumptions, vulnerable/fixed pairs and hard negatives. Do not submit real secrets, proprietary source, private repository identifiers or real account/session data.

Release preparation requires a new package version, matching report version, built Host/Client outputs, an immutable tarball, catalog identity/size/SHA-256 validation, a real isolated official-profile startup, packaged CLI verification, and sanitized public export verification. Keep dependency locks and checksum enforcement enabled. Never replace different bytes under an existing release identity. Publication, push and updating a user's installed profile are separate actions.
